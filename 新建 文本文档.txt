第一章	需求分析
1.1项目背景与问题陈述
在终身学习时代，个人学习管理面临着目标模糊、时间碎片化、资源过载和动力不足四大核心挑战。现有的学习管理工具——TODO应用、日历工具、打卡软件和资源平台——各自解决了部分问题，但由于功能割裂、缺乏AI辅助、无法形成闭环，用户不得不在多个工具间手动同步数据，认知负担显著增加。
大语言模型技术的成熟为解决上述问题提供了新的可能性。AI能够理解自然语言输入，自动完成目标拆解、资源筛选、文案生成等复杂任务，将用户从繁琐的计划和管理工作中解放出来。
基于此背景，SmartPlanner旨在构建一个AI驱动的智慧学习助手，实现从“目标设定”到“任务拆解”到“智能排程”到“资源推荐”到“打卡反馈”再到“画像优化”的完整管理闭环。
1.2用户角色分析
SmartPlanner主要面向三类用户群体：
日常学习者包括在职人员和自由职业者，其典型特征是有持续学习意愿但时间碎片化，核心需求是将模糊目标转化为可执行任务并合理安排到零散时间中。
备考学生包括考研、考证等备考人群，其特征是目标明确但有时间压力，有固定的课程表，核心需求是将复习任务自动排入空闲时段并获得资源推荐。
习惯养成者关注持续的小行动，核心需求是通过打卡获得正向反馈，并从数据中了解自己的进步轨迹。
1.3功能需求
目标与任务管理方面，用户应能创建自然语言描述的学习目标，系统调用大语言模型将目标自动拆解为层次化任务树。任务包含名称、预估时长、优先级和截止日期等属性。拆解过程异步执行，完成后通过通知告知用户，失败时提供重试和手动添加的降级方案。
课表与排程管理方面，系统应支持导入CSV格式课程表，解析课程信息并自动计算每日空闲时段。智能排程功能将待办任务按优先级和截止日期排序，排入空闲时间，生成多个候选方案供用户选择确认。用户确认后生成正式排程记录。
资源检索与推荐方面，系统维护学习资源库，支持标题、主题等字段的全文检索。系统自动推荐相关资源：优先使用 Elasticsearch 全文检索，不足时回退到数据库模糊匹配。RAG 向量语义检索用于用户随笔和画像分析场景（user-service），资源检索本身不走向量路径。资源推荐采用异步Job方式执行，避免前端超时。
打卡与画像分析方面，用户可提交每日打卡记录，系统统计准时率、完成率和连续打卡天数。基于打卡数据生成个性化洞察和学习建议，支持画像实时重算。
智能助手方面，系统提供流式对话交互，助手可通过工具查询任务、排程、打卡和随笔等真实数据，严禁编造。系统能基于连续打卡、未完成任务数量、随笔情绪词等规则主动推送关怀提醒。
1.4竞品对比
根据调研，我们得出了以下对比表格：
维度	传统排程软件	SmartPlanner
空闲时间识别	需用户手动指定可用时段	自动读取课表，识别离散空闲时段
模糊目标处理	用户自己拆解、研究子任务	AI自动拆解为可执行任务
资源查找	自己去各个平台搜索	排程完成后自动检索关联资源

第二章	概要设计
 
设计架构图
2.1系统定位
SmartPlanner 是一个面向个人学习场景的微服务应用，实现从“目标设定 → 任务拆解 → 智能排程 → 打卡反馈 → 画像建议”的完整学习闭环。
2.2服务架构
系统由七个业务微服务加一个监控服务构成。网关服务（gateway-service）作为统一入口，负责路由、JWT 鉴权、API Key 校验和 Redis 秒级限流。用户服务（user-service）是中枢聚合层，承担认证、仪表盘聚合和内部接口，通过 Feign 协调调用其他服务。AI 智能体服务（agent-service）独立运行，承担 Agent 对话、RAG 向量索引、用户画像分析和智能提醒推送。目标服务（goal-service）管理目标与任务，通过 MQ 异步调用 AI 完成目标拆解。排程引擎（schedule-engine）处理课表导入、空闲时间计算和任务智能排程。资源检索服务（resource-search）管理资源库，提供 ES 全文检索、kNN 向量语义检索和多平台爬虫。打卡服务（punch-service）记录学习打卡行为并生成习惯数据。监控服务（admin-server）基于 Spring Boot Admin，通过 Nacos 自动发现所有服务，提供健康、指标、日志、环境变量等统一监控面板。
2.3基础设施
系统依赖 Nacos（服务注册发现）、MySQL（sp_user/sp_goal/sp_schedule/sp_resource/sp_punch 五个独立数据库）、RedisStack（缓存 + 向量语义检索，基于 HNSW 算法）、RabbitMQ（异步任务与通知，含死信队列）、Elasticsearch（资源全文检索索引）。全部服务通过 Docker Compose 容器化部署，支持一键启动与编排管理。
2.4核心数据流
同步请求路径为：前端经网关到达用户服务，再通过 Feign 调用下游服务，结果逐层返回。异步任务以目标拆解为例：创建目标后向 MQ 发送拆解任务并立即返回，消费者调用 AI 完成拆解并写入数据库，随后发送通知，用户服务通过 SSE 实时推送给前端。该设计避免了同步等待导致的超时问题。
2.5关键技术要点
鉴权与上下文：JWT 认证，网关解析后通过请求头向下游透传 userId 等用户信息。
AI 接入：统一使用 Spring AI Alibaba 接入 DashScope（qwen-max），针对不同业务场景设置分层超时控制，关闭自动重试。
排程逻辑：基于课表计算空闲时段，支持多候选方案供用户选择确认，排程任务以异步方式执行。
检索与去重：资源检索采用 ES 全文检索优先、AI 增强补充的策略。去重通过 URL 归一化（如处理 B 站分 P 链接）和标题归一化实现。
通知机制：RabbitMQ 解耦业务与通知发送，用户服务消费通知后通过 SSE 长连接推送到前端铃铛与 Toast。
异步化解耦：目标拆解、资源推荐、日计划等耗时操作均采用 MQ 或 Job 模式，避免前端请求超时。
 
Docker容器化部署
容器化部署：基于 Docker Compose 实现分布式微服务的容器化自动部署，支持多服务一键启动与编排管理。
第三章	详细设计
 
产品主界面
3.1项目重点
通过 AI 自动将目标拆解为可执行任务，基于课表空闲时间智能排程并支持候选方案确认；资源检索采用 ES 全文检索与向量检索相结合，并为任务自动推荐课程；打卡数据驱动习惯画像与学习洞察；Agent 对话与感知提醒提供个性化的复盘与建议；全链路通过异步任务和 SSE 推送保证响应体验，形成从目标到任务、排程、打卡、画像的完整闭环。
3.2项目特点与设计
（1）总体结构设计
为解决异构技术栈（MySQL + ES + RedisStack向量检索）的统一治理与耦合问题、AI慢任务与核心轻量接口之间的故障隔离与独立扩展需求，以及期末、考证高发期带来的高并发压力下，不同模块（如排程、资源检索、打卡）需要差异化弹性扩容的能力，所以采用微服务架构。

（2）AI任务拆解设计
目标拆解采用异步消息队列模式。用户通过 AiTaskOrchestrator 提交目标描述后，系统立即写入数据库并发送 MQ 消息到 goal.ai.queue（配置了死信队列 DLX→DLQ 防止消息丢失），接口随即返回。GoalAiWorker 消费消息后，先调用 DashScope 大语言模型进行拆解（AI 调用在事务外），提示词经 AiResponseParser 净化（过滤禁止词/日期时间伪造），输出包含任务名称、预估耗时、优先级、依赖关系的 JSON 数组。拆解结果通过 TransactionTemplate 精确控制事务边界批量写入任务表，再通过 Feign 异步预绑定资源到 Redis，最后 SSE 通知前端。任务创建使用 TaskService 的 bigram Jaccard 标题归一化去重，防止重复拆解。

（4）智能排程设计
排程引擎由 FreeTimeCalculator、ScheduleImportService、ScheduleValidator、TaskScheduleService 等多个组件协同工作。FreeTimeCalculator 基于课表解析每日空闲时段并合并连续碎片。排程推荐模型采用连续映射多因子决策：将任务优先级评分从三档硬切升级为 avg×0.8→clamp[25,90] 连续映射，叠加拖延罚分、休息比例缩放（×0.25）、每日上限三维决策（完成率分档 + 拖延罚分 + 新手保护）。支持生成多个候选方案供用户确认，PlanCandidateWorker 异步处理候选方案 AI 建议。排程结果写入日程表后通过 SSE 实时推送前端。
（5）RAG资源检索设计
资源检索采用多级策略。快速模式通过 Elasticsearch 全文检索标题与摘要字段返回资源列表。kNN 向量检索模式：资源内容经 DashScope Embedding 向量化后存入 RedisStack（HNSW 索引，Cosine 距离），用户查询同样向量化后通过 kNN 语义匹配返回最相关资源，支持按 userId/type/goalId 等标签字段过滤。增强模式将检索结果作为上下文输入大语言模型，输出推荐理由与筛选后的资源。去重机制包含 URL 归一化（处理 B 站分 P 链接）、标题清洗归一化（全角转半角、去特殊字符）和近似比较三层过滤。此外，系统内置 6 平台爬虫（B站/GitHub/掘金/慕课网/CSDN/博客园），通过 CrawlerOrchestratorService 编排并行爬取，爬取结果自动写入 ES 索引并通过 SSE 实时通知前端。
（6）用户画像建模
画像基于打卡记录实时计算，指标包括近七天准时率、完成率、平均延迟、连续打卡天数。系统定期调用AI分析上述数据，生成个性化学习建议与推荐参数，结果缓存至Redis并设置过期时间，过期后自动触发重新计算。
（7）通知系统设计
通知系统基于RabbitMQ与SSE构建。业务服务向通知交换机发送消息，用户服务消费后通过SSE长连接推送给对应前端。前端根据通知类型分别触发Toast弹窗、铃铛角标更新或页面静默刷新。连接断开后前端自动采用指数退避策略重连。
（8）网关限流与鉴权
网关配置四层过滤器链：ApiKeyAuthFilter（order=-100）验证 X-API-KEY 头部，UserContextForwardFilter（order=-90）解析 JWT 令牌并向下游透传 X-User-Id/X-Username/X-Roles 请求头，RedisRateLimitFilter（order=-80）基于用户 ID 或 IP 进行秒级计数限流（默认 10 req/s），超出阈值返回 429，SecurityWebFilterChain 双链设计——白名单链（/api/auth/** + /actuator/**）放行登录注册和健康检查，保护链要求其余 /api/** 路径携带 JWT Bearer Token 并支持 URL query parameter 传 token。流式接口的响应头设置需在 beforeCommit 回调中完成，避免连接提前关闭。
（9）Agent 智能对话与流式输出
Agent 服务（agent-service）作为独立微服务运行，承担所有 AI 对话、RAG 向量索引、用户画像分析和智能提醒功能。基于 Spring AI Alibaba ReactAgent 和 RedisSaver 实现多轮对话，通过 10 个被 @Tool 注解标记的方法获取真实数据，严禁模型编造任何事实信息。Agent 系统提示词按问题类型路由至不同工具组合（打卡类→listPunchRecords、随笔类→直接注入 Feign 数据绕过 LLM 工具调用、任务排程类→listTaskSchedules 等），确保数据准确性。输出内容经过 chatTextUtils 过滤 Markdown 残留标记和冗余空行，并在建议用户操作时在末尾追加跳转链接。流式输出方面，后端使用 StreamingResponseBody 边写边 flush，网关在 beforeCommit 阶段设置禁缓冲响应头，Nginx 关闭 buffering 和压缩，前端通过 ReadableStream 持续读取并增量渲染，实现端到端真流式输出。
3.3关于使用流程的简要说明
 
上传课表后分解目标界面
首先在“学习计划向导”中按顺序操作：导入课表（一次即可），系统自动识别空闲时间，然后添加新目标。创建目标后，AI 会自动将目标拆解为可执行任务，接着前往目标页面进行智能排程，将任务安排到空闲时段。最后在日程中完成打卡即可。
课表已导入的用户无需重复上传，可以直接开始添加目标。排程完成后，系统会推送通知，并在任务卡片旁自动展示相关的课程资源推荐。
 
AI拆解任务界面
 
校内课程与额外计划的混合可视化显示
如上图所示，当用户添加“学习分布式系统”目标后，AI 将其拆解为 8 个具体任务，包括阅读基础概念、练习 CAP 定理、写作一致性模型比较、搭建 Kubernetes 集群等。页面底部提供“满意”和“不满意”两个选项：点击“满意”可直接前往目标页进行智能排程，点击“不满意”则触发 AI 重新拆解，确保任务规划符合用户预期，避开上课时间。
 
用户随笔记录心情界面
除学习规划与执行，系统还提供随笔记录功能。用户可以随时记录学习心得、成就或情绪状态，如截图中记录“获得ICPC金奖”并标记开心心情。这些随笔数据会被 Agent 用于后续的复盘分析、情绪感知和个性化提醒，例如当用户连续多日未写随笔或出现消极情绪时，系统会主动推送关怀提醒。
 
智能体使用界面
最后Agent 是贯穿整个学习过程的智能助手，通过函数调用能力与后端 10 个工具方法联动，能够真实获取用户数据而非编造回答。用户可以随时向 Agent 提问，例如询问“今天该做什么”，Agent 会调用排程工具返回当天的具体任务安排及时间；询问“我最近的状况如何”，Agent 会综合打卡记录和随笔内容进行总结并给出鼓励建议；询问“总结最近一周随笔”，Agent 会调用随笔列表工具提取原文片段进行复盘分析；询问天气时，Agent 会自动读取用户保存的城市并返回实时天气信息。Agent 还支持创建随笔、添加任务、触发排程等写入操作，所有回复末尾自动附带跳转链接，方便用户一键进入相关页面继续学习。整个对话采用流式输出，回答边生成边显示，体验流畅自然。
第四章	测试报告
4.1测试环境
Docker Compose 全量部署，测试机 4核8G。使用 Postman、JMeter 及浏览器开发者工具进行验证。
4.2功能测试
用户注册登录、JWT 鉴权流程正常，Token 过期刷新机制有效。创建目标后接口立即返回，5-15 秒内收到 SSE 通知及 AI 拆解的子任务，重复创建不会产生重复拆解。导入课表后空闲时段计算准确，自动排程能将任务无重叠地分配至空闲时段，支持生成多个候选方案供用户确认。资源检索的 ES 全文检索按相关性排序返回结果，增强模式可附加推荐理由，B 站分 P 视频链接被正确归一化去重。Agent 流式对话呈现打字机效果，能基于真实数据回答，支持跳转按钮渲染。SSE 连接在登录后自动建立，收到排程完成等通知时右上角铃铛正确提醒，连续重复通知在 2 分钟内被去重。
4.3性能测试
并发 50 用户下，注册登录平均响应 80 毫秒，创建目标 50 毫秒（异步返回），任务列表查询 30 毫秒（缓存）。ES 检索 120 毫秒，增强模式 3-5 秒（已改为异步）。AI 拆解吞吐每分钟 30-50 个，排程任务每分钟 200 个。SSE 连接持续 8 小时未中断，断线后自动重连成功。
4.4异常测试
AI 服务不可用时，30 秒后收到失败通知，目标状态更新为失败，系统不卡死。数据库短暂中断后连接池自动恢复，故障期间请求返回 500 但恢复后正常。同一目标重复创建被幂等控制拦截，仅保留一条记录。流式对话中断后后端无异常堆积，前端可正常发起新对话。
4.5结论
所有核心功能验证通过，异步解耦有效避免前端超时，SSE 推送稳定，流式体验达到预期。生产部署前需更换默认密钥及 API Key，并根据实际流量调整限流阈值。
第五章	安装及使用
5.1环境要求
系统推荐使用 Docker Compose 一键部署，要求机器具备 4GB 以上内存和 Docker 运行环境。若采用本地开发模式，则需 JDK 17、Maven 3.8 及 Node.js 18。
5.2安装步骤
首先在项目根目录复制 .env.example 为 .env 文件，填入有效的 DashScope API 密钥。然后执行 docker compose up -d --build 命令启动所有服务。首次启动约需三至五分钟，使用 docker compose ps 确认所有服务状态均为 Up 即可。
5.3访问地址
前端页面位于 http://localhost:5175，后端 API 网关位于 http://localhost:8088。Nacos 控制台位于 http://localhost:8848（nacos/nacos）。Spring Boot Admin 监控面板位于 http://localhost:9090（admin/admin123）。RabbitMQ 管理台可通过 http://localhost:15672 访问，预设账号为 sp/sp123。
5.4使用流程
用户首先注册账号并登录。进入「学习计划」页面上传 CSV 格式的课表文件，文件需包含课程名称、星期、开始时间和结束时间。随后在「目标」页面输入学习目标，例如“四周学完计算机组成原理”，系统将在五至十五秒内通过 AI 拆解为子任务，并通过右上角通知提醒用户。
在目标详情页勾选子任务后点击「排入日程」，系统基于课表空闲时段生成多个排程方案供用户选择确认。完成学习后进入「打卡」页面记录完成情况，系统会据此生成本周准时率、连续天数等画像数据。
点击右下角图标可唤起 Agent 助手，支持自然语言提问，如“今天还有哪些任务没完成”或“推荐学习资源”。回答以流式逐字显示，末尾若含跳转标记则可点击直接导航至对应页面。
5.5本地开发
执行 docker compose up -d mysql redis rabbitmq elasticsearch nacos 启动基础中间件，然后依次运行各微服务的 Spring Boot 启动类。前端进入 web-front 目录执行 npm install 与 npm run dev 即可。
第六章	项目总结
SmartPlanner 是一套面向个人学习场景的微服务应用，围绕“目标设定→任务拆解→智能排程→打卡反馈→画像建议”构建完整学习闭环。
系统采用微服务架构，包含网关、用户、AI智能体、目标、排程、资源检索、打卡七个业务微服务和一个监控服务，依赖 Nacos、MySQL、RedisStack、RabbitMQ、Elasticsearch 等基础设施。关键技术包括 JWT 鉴权与用户上下文透传、API Key 服务间认证、Redis 秒级限流、基于 DashScope 的 AI 能力接入、MQ 异步化解耦耗时操作、SSE 实时通知推送、kNN 向量语义检索与多平台爬虫，以及流式 Agent 对话。
项目创新点在于将大语言模型深度整合至学习管理的各个环节：AI 自动拆解学习目标、kNN 向量语义检索增强的资源推荐、基于真实数据的 Agent 智能对话与关怀提醒、连续映射多因子排程推荐模型。异步任务机制有效解决了 AI 调用慢导致的前端超时问题。项目已完成 198 个单元测试（common 3 + goal-service 49 + schedule-engine 52 + agent-service 等），核心模块零回归。经过完整功能测试、性能测试与异常场景验证，系统核心流程通畅，异步解耦设计合理，SSE 推送稳定可靠。该项目为个人学习管理提供了智能化、个性化的完整解决方案。
进一步提升点在于当前系统尚未正式分布式事务方案，在涉及多服务数据一致性的场景（如打卡后同步更新画像和习惯数据、排程完成后跨服务写入任务状态与资源推荐记录）存在理论上的数据不一致风险。后续可引入 Seata 分布式事务框架，采用 AT 模式或 TCC 模式对关键写路径进行事务管理，确保跨服务操作的数据最终一致性与业务完整性。
